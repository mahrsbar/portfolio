Writing · Design systems · Agents

I generated the same component library twice. The second one worked.

March 2026

Within six months I built the same design-system component library two ways. First with scripts that turned Figma exports into React. Then with a coding agent working from live design context and a rules file. The second was better by every measure that mattered, and the reason had nothing to do with which approach was "smarter".

Build one: scripts

The pipeline was tidy. A Figma plugin exported each component as JSON: prop names, variant options, sizes, a deep link. A build script read the JSON and generated a React wrapper around the matching MUI component, a Storybook story with a control per variant, and token docs. I built it with Claude Code on Sonnet 4.5 in a few weeks. It scaffolded sixteen components in one run.

Then we opened Storybook.

  • Toggles didn't toggle. Every wrapper was stateless.
  • Chips crashed. A boolean was being passed where MUI wanted an icon element.
  • Hover, focus, and active states were missing. The state mapping only knew about disabled.
  • Nothing used a design token. Every component had fallen back to generic MUI styling.

The heart of the system was a mapping file: 712 lines translating Figma prop names into MUI prop names. When I audited it, 62 percent of entries were pass-throughs that added nothing, twelve were broken and produced the bugs above, and five were genuine renames. The hard parts of a component, composition, controlled state, tokens, and rendering logic, were outside its vocabulary entirely.

The scripts produced the shape of each component. They couldn't produce the component, because they had never seen it.

Build two: an agent with rules

The second approach kept the plugin JSON as the source of truth for props and variants and threw away the generators. In their place: an agent in Cursor, with two inputs the scripts never had.

Live design context. Through Figma's MCP server the agent could see the component's actual render, its variable bindings, and its auto-layout values. It wrote from what the component looked like, not from a list of property names.

A rules file. A workflow document that loads into every session and encodes how a component in this codebase gets built. Read the two reference components first. Extract the MUI API from MUI's own MCP server, never from memory. Map every Figma pixel to a named token and stop if the tokens file is stale. Build theme override, wrapper, stories, tests, manifest, in that order. Verify with a deterministic spec diff and a measured visual diff before reporting done.

Fourteen components came out. All of them passed type-check and visual regression. All of them worked when clicked. The mapping file was deleted; the agent wrote the one-line translation directly in each wrapper, where it's readable and type-checked.

It wasn't speed, and it wasn't the model

People hear "the agent replaced the scripts" and assume it won on velocity. It didn't. The scripts were faster. The agent was slower per component and every component was reviewed.

It also wasn't primarily the model. The turning point was Claude Opus 4.6, and I documented the comparison at the time, but later models on the same rules produced the same quality. What changed was the two inputs. A generator applies rules to data. The agent applied rules to data and to a picture of what the data should become.

The second shift was where judgement lives. In build one, judgement was code: seven hundred lines that had to anticipate every case. In build two, judgement is prose. When the agent made a recurring mistake, say styling a Chip's icon slot inconsistently, the fix was a sentence in the rules file, not a parser change. That file now ends with a table of every real failure from earlier sessions, each paired with the rule that prevents it. It is the most valuable thing in the repository.

What carried over

Build one wasn't wasted. It forced the export format to become canonical, which made the agent's job easier. And the theme-first architecture that emerged in build two, tokens mapped into MUI theme overrides with most components as pure re-exports, was a direct reaction to build one's hard-coded wrappers.

Where I'd still use scripts

Anything mechanical: token transforms, documentation tables, checking that every story has a design link, generating the manifest. Scripts are excellent at the parts of a design system that don't need to know what a component is for. Knowing which parts those are is the actual job.
