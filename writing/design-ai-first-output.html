Design the input: AI-readable JSON is just good JSON

February 2026

I built a Figma export plugin for a build script. Somewhere along the way its main reader became a language model. Every change I made to help the model also helped the script, and helped the humans reading the file. That isn't a coincidence, and it changed how I think about formats.

What a model needs

A language model is very good at completing patterns and very bad at guessing which of two inconsistent things you meant. Give it a file where the same concept is colours in one branch and color in another, where a variant is "Contained" here and "contained" there, where a slot exists as both a boolean and an instance swap, and it does what any reader does: picks one, silently, and is wrong half the time.

So the things that make output good for a model are:

  • Determinism. Same input, same bytes. No iteration-order surprises.
  • Canonical names. One name per concept, matched to the target domain. If code says leftIcon, the export says leftIcon, not the designer's "Leading icon".
  • No duplicates. If a slot can be described two ways, pick one and hide the other.
  • Semantic structure. Nesting that mirrors meaning, not the tool's internals.
  • Stable references. Links and IDs in the exact shape the next tool parses.

Before and after

Here is roughly what a component looked like coming out of a typical exporter, and what it looks like coming out of mine.

// before: one entry per variant node, Figma's names, Figma's casing
{ "Button / Contained / Primary / Large": { "Colours": "Primary", "Leading icon": true, "Leading icon#123:4": "Icon/Add" } }
{ "Button / Contained / Primary / Medium": { ... } }
// ... ninety-eight more

// after: one entry per component set, canonical names, options as unions
{
  "Button": {
    "variant":  { "type": "VARIANT", "options": ["contained", "outlined", "text"] },
    "color":    { "type": "VARIANT", "options": ["primary", "secondary", "error"] },
    "size":     { "type": "VARIANT", "options": ["small", "medium", "large"] },
    "leftIcon": { "type": "INSTANCE_SWAP" },
    "figmaUrl": "https://www.figma.com/design/FILE/Name?node-id=12-345"
  }
}

The second one is what the model reads. It is also what the build script reads, what the Storybook controls are generated from, and what an engineer pastes into an editor. Same file, four readers, no translation.

Now reread the list as a human

Deterministic output diffs cleanly in a pull request. Canonical names mean you don't grep for three spellings. No duplicates means one Storybook control per slot. Semantic structure means you can find things. Stable links mean the design tab actually opens the design.

"AI-readable" turned out to be a stricter, more honest name for "well designed".

Naming was most of the value

Of everything in the plugin, the piece that delivered the most was the least glamorous: a dictionary mapping designer vocabulary to code vocabulary. It removed a whole category of cleanup, equally for the script, the model, and the engineer. The rest (alias resolution, four deduplication passes, breakpoint cleanup) is plumbing that exists because source data is messy. Important plumbing, but plumbing.

A test I use now

For any machine-readable output: if I handed this file and nothing else to a capable stranger, could they do the job without asking me anything? The stranger might be a model, a new teammate, or me in six months. A file that satisfies one satisfies all three.

Which is why I think designers and UX engineers belong in the room when data formats get decided. Format design is interface design. The user is a program, and increasingly a program that reads like a person.
