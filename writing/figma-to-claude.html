Five ways to get a Figma design in front of Claude

October 2026

"How do I send a Figma file to Claude?" hides a choice: how much of the design should Claude actually receive? A picture, the exact values, the variables, the real icons? Five ways, what each one hands over, what it drops, and when I use it.

1. Paste a picture

Setup: none. Fidelity: low. Direction: Figma → Claude, Claude Design or Claude Code.

Export the frame as a PNG (or copy it as one) and paste it into the chat, or into a Claude Design project as a reference image. Claude Design is built for this: screenshots, wireframes and competitor products are exactly the context it asks for.

What you get is a model looking at a picture. It will reproduce the layout convincingly and approximate everything else. Colours come back close but not exact, spacing gets rounded to whatever the model considers normal, icons get redrawn from memory or swapped for a library that "looks similar", and the text is retyped. Pasting an SVG instead of a PNG keeps the vectors but tells Claude nothing about layout.

That's fine when the design is an idea rather than a spec. For "make me something like this", a picture is the fastest input there is. For "make me exactly this", it's where every round of feedback begins.

2. Connect the Figma MCP server

Setup: one command. Fidelity: high. Direction: Figma → Claude Code (not Claude Design).

Figma's MCP server lets an agent read a file directly. In Claude Code the recommended path is the Figma plugin, which bundles the server settings and the skills below; the manual route is claude mcp add --transport http figma https://mcp.figma.com/mcp. Then you paste a link to a frame or a layer and ask for it to be implemented. Claude Code can't follow the link, but the server extracts the node from it.

The server's main tool, get_design_context, returns a structured representation of the selection with its exact values. get_variable_defs returns the variables and styles in use, so colours arrive as colour/button/border-focus instead of a hex guess. get_screenshot gives the agent something to check its work against, and get_metadata is the fallback when a frame is too big to return in one piece.

Three things to know before you rely on it. It needs a Dev or Full seat on a paid plan for real use (up to 200 tool calls a day, 600 on Enterprise); View and Collab seats get up to 20 a month, which is enough to try it and not enough to work with. Large frames time out or come back truncated, so break a screen into its sections. And the agent still has to map Figma's component instances to your components: without Code Connect it will happily build a Button from divs.

This is the one I use for real product work, because it's the only option where the agent reads the live file. The design-system rules I wrote for Cursor name the server as the authoritative source of design truth: if it's unavailable, the agent must stop, not guess.

3. Add the Figma skills

Setup: included with the plugin. Fidelity: same as the server. Direction: both.

The skills are pre-written instructions that teach the agent common Figma jobs, so you can say "implement this design" or "create a new Figma file" without describing each step. They come with the plugin for Claude Code, Cursor and Codex, or as a zip you drop into your tool's skills folder.

Most of them point the other way, from code into Figma. figma-use creates and edits frames, components, variables and layouts in a Design file (it needs edit access and a file link). figma-code-workflows imports a local project into Figma, which needs a Full seat and can take ten minutes or more. The one I'd single out for design-to-code is figma-code-connect: it links published library components to your code, so get_design_context can say "this is your Button" instead of describing a rectangle with text in it. It needs a published team library and a Professional, Organization or Enterprise plan.

4. Bring the design system into Claude Design

Setup: an afternoon. Fidelity: high for the system, none for a specific frame. Direction: Figma → code → Claude Design.

Claude Design has no Figma connector. It can't read a Figma URL or a .fig file, and nothing in its import list mentions Figma. What it can take is a design system from a GitHub repo, design files, raw uploads, or the /design-sync command in Claude Code, plus a linked code repository so it understands your existing components and styling.

So the route from Figma runs through code. Get the tokens and component definitions out of Figma as files (the MCP server's get_variable_defs will do it; my export plugin writes them as Style Dictionary JSON with every variant and its options), commit them to the repo, and point Claude Design at it. From then on, screens it generates use your colours, type and spacing by name, and your components where it knows them.

The cost is that nothing is live. When the Figma library changes, you re-export and re-sync. For a design system that changes weekly that's a chore; for one that changes quarterly it's a non-issue. This is the way I'd pick for exploring new screens quickly inside an existing system, which is what Claude Design is good at.

5. Export a handoff bundle

Setup: a plugin I built. Fidelity: highest for one frame. Direction: Figma → a zip → any Claude.

After watching agents implement frames from the MCP server for a while, I noticed the failures were never code problems. They were context problems: an approximated colour, a hand-drawn icon, a font silently swapped, "close enough" after one pass. So I built a Figma plugin that stopped trying to write code and instead packages everything the agent needs to write it: spec.json with the full tree and exact values, frame.png as a ground-truth render, the real SVG and image bytes in assets/, and a handoff prompt.

The prompt is the part that matters. It names the exact field paths ("canvas size is in meta.size, per-node size is tree.size, not node.width"), defines done as an iteration loop against the PNG, and lists the shortcuts I'd watched agents take: measuring pixels off the screenshot instead of reading the spec, swapping an icon for one that "looks similar", calling it done after the first pass. The full list is on the design-system page.

The plugin needs no network access, so the bundle is a zip you drop into Claude Code or a Claude project yourself and nothing leaves the machine, which matters when the frames are internal product screens. The trade-off is that it's a snapshot of one frame, not a link to a live file. I reach for it when a single screen has to be pixel-faithful and I want the agent to stop guessing.

What I actually do

Pictures for ideas. The MCP server for anything that ships, with Code Connect once the library is published. The export plugin and a repo sync for Claude Design, so the screens it dreams up are at least in our colours. And the handoff bundle when a specific frame has to match and I've already watched the agent get it wrong once. Each step up the list costs more setup and gives the model less room to improvise. The better the input, the less the output needs fixing.
