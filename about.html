About

I design and build for how people actually behave.

I'm a UX Engineer in Vancouver with 7 years of building software, currently at GeoComply. I start with user research to find out how people actually work, shape what the product should become, and build it in React and TypeScript, down to the design system it runs on.

The short version

I studied psychology first, then computer science. Before I wrote any production code I'd spent years on attention, memory, decision-making and how people behave when a system surprises them. So when I learned to build software, I already knew who I was building it for.

I've been a front-end and full-stack developer, a technical lead, and now a UX engineer. In every role I've worked on both the design and the code. I like understanding the problem, building the fix, then making a tool so the next one is easier.

What the psychology background actually changes

  • I start with behaviour data. Session replays, support-channel history, shadowing. I want to know what people do before I ask them what they want.
  • I design for what goes wrong. A dead-end error becomes a support ticket, and an unclear state sends people in circles. The licence application redesign was mostly about making the next step visible.
  • I keep cognitive load in the budget. Fewer navigation choices, one organising element per page, empty states that are never confused with loading states.
  • I treat AI as a user too. An LLM reading a JSON file has the same problem as a new teammate: ambiguity costs it. Getting the input right has mattered more than anything else I've done with AI.

Human factors, formally

Most of the psychology I use comes from human factors: Rasmussen's skills-rules-knowledge model of where operators fail, ecological interface design (make constraints obvious so attention goes to the real problem), signal detection theory (why a false "no results" is worse than a slow one) and universal design. Each case study here applies one such principle to a real decision.

How I use AI

AI does a lot of my building now. Most of my job is deciding what to ask it for, and checking what comes back.

  • What I've shipped with it: LoafMode, live on the App Store, art included. An AI investigation assistant (React, Cloudflare Workers, Claude API) that turns analysts' questions into editable filters. Four Figma plugins and an AI-agent pipeline that cut design-to-code from days to about 10 minutes. And a component library rebuild, after the first AI-generated version looked right and didn't work, now used by 4 products.
  • Tools: Claude Code for my own projects, and Cursor with a shared rules file for the team's library. Figma MCP so the agent sees the real frame, MUI MCP so it reads the docs instead of guessing. Figma Make and Claude Design for prototypes, Claude Projects for research notes.
  • What stays mine: deciding what to build, anything that touches credentials or customer data, and the call on whether a screen actually matches the design.
  • How I check its work: tests that assert exact values, visual diffs against Figma with a threshold, and a running list of every mistake the agent made, each turned into a rule or a test so it doesn't happen twice.

Models I've shipped with, from git: Sonnet 4.5, Opus 4.6, 4.7 and 4.8, Opus 5, Fable 5.

What I'm working on now

A Figma-to-code pipeline an AI agent can run without someone translating in between, and turning scattered investigation tools into one experience with room for AI features.
