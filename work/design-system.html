Case 01Design system

A design system four products run on

Our design system only existed in Figma. I cleaned it up with Figma plugins I built with AI, had an agent generate the component library in a few days, found out why it only worked in Storybook, and rebuilt it theme-first, so 66 MUI components take their look straight from design tokens.

The problem

The design system looked finished in Figma, but it was a picture of a system. The coded library underneath had no foundation: the MUI theme set a font and nothing else, with no design tokens. Every component carried its own hard-coded CSS instead (the Button alone was 370 lines), so changing a colour or a spacing value meant hunting it down component by component.

The Figma file couldn't have fed a better library anyway: dozens of near-duplicate text styles, colours painted on instead of linked to variables, and spacing that existed only as numbers.

Step 1

Clean up Figma, without doing it by hand

Code generated from a messy file is just messy code, so the file came first. By hand, that meant re-pointing every text style and value one at a time: 1,516 properties on just two component sets. So I built two Figma plugins with Claude Code instead: one for type, one for everything else.

Plugin 1Tokenization for type

Created the type variables (size, weight, family, line height), merged text styles that shared a size and weight, swapped every use onto four shared groups, and deleted the duplicates.

One run covers every page, component and nested instance in the file, then reports anything it couldn't convert.

→ →

One text style group per component, each redefining the same few sizes under new names. Look at button: large and medium are both 14/20. Breadcrumb default, underline and button small are all 12/16.

Every component style mapped to a shared one, across every page.

Four shared groups (heading, body, small and xsmall) replaced one per component. Every style now reads its size, weight and line height from a variable, so changing body text across the whole file is one edit, not a hunt through every component.

Plugin 2Variable relinker for everything else

Creates nothing new. It connects colours, padding, gaps, radii and stroke widths to the variables that already exist, and repairs broken links. 1,516 properties in its biggest run.

Figma's built-in fixes can reconnect a variable to its library or detach a dead one. They can't turn a raw 12 into space-12, or point a dead variable at its replacement. This does both.

Two kinds of mess: values typed in by hand, and links to variables that no longer exist.

Each value matched to a live token. Anything without one is flagged, not guessed.

Step 2

Version one: generated in days, hollow underneath

With a clean file, I needed it in a form code could read, so I built a third plugin to export it.

Plugin 3Figma export from Figma to code

Exports variables, components and icons as JSON with consistent names that a script, an engineer or a model reads the same way. A Button with a hundred variant nodes comes out as one component with its options. A re-export that used to mean six to eight hours of hand fixes now takes about ten minutes and none.

Badge.json, simplified: every variant and its options, plus a deep link the agent uses to read the live design. Node IDs and file keys removed.

Plugin 4Handoff bundle for any frame

Packages one frame for an agent instead of writing code for it: the full spec with exact values, a ground-truth render, the real SVG and image bytes, and a prompt that tells the agent where every value lives and what "done" means.

The prompt is the product: its list of shortcuts that fail is every mistake I watched an agent make. How it compares to the MCP server and Claude Design.

From the handoff prompt · shortcuts that fail
  • "The spec is large, I'll be efficient and skip parts." It fits in context. Read all of it.
  • "I can't find the dimensions, I'll measure the PNG." Every node has size.width. The PNG is for checking, not measuring.
  • "I'll substitute Lucide or Heroicons, they look similar." The exact path data is in svgInline. Use it verbatim.
  • "This text seems off, I'll fix it." A badge that says 3 says 3.
  • "This looks close enough, calling it done." Render, compare to the PNG, fix, repeat.

Then I had an agent in Cursor generate the library from that export. In a few days it produced 33 components, 156 Storybook stories and 420 passing tests. Then I tried to build a real screen with them.

  • You couldn't read their values. 22 of 33 components kept their own internal state. A Switch toggled on screen but never told the app it had changed.
  • Seven were showcase pieces. The Menu rendered five hard-coded “Menu item” rows and had no way to pass items, open it, or anchor it to a button. Dialog, Select, Tabs and others were the same: perfect in Storybook, unusable in a product.
  • Behaviour had become a dropdown. 18 components had a state prop with options like “hover” and “focus”, turning things the browser handles into settings you pick.
  • The tokens were ignored. 75 raw hex and rgba values, despite a token file generated for exactly this.
  • Nothing was accessible. Zero ARIA attributes across the library, and a radio button you could click off.
  • The tests couldn't see any of it. All 420 tests searched the source code for strings. None rendered a component, so every one passed while the components were broken.

My rules told it to build on MUI, and it did. The problem was who the rules were written for: Storybook. Every component had to be interactive in Storybook, so each one kept its own state. Every Figma property had to be a Storybook control, so hover and focus became a dropdown. Icons had to be picked from a list, so you couldn't pass your own. Each rule made sense on its own; together they wrapped MUI so tightly that product code lost everything MUI normally gives you: children, onChange, anchoring, keyboard support.

And where the rules were right, nothing enforced them. They said never hard-code a colour; the library had 75. They said build from our own components; the group components imported raw MUI and restyled it inline.

The lesson

AI builds exactly what you ask for. I asked for Storybook, so I got Storybook.

Step 3

Version two: a contract, then an architecture

So version two started by changing what “done” meant. I audited everything first: a QA report per component, 38 of them. Most failures came from a few systemic causes: hard-coded colours and pixel values in 31 of the 38, runtime tests that existed for only two components, group wrappers importing raw MUI instead of our own atoms, and state held where none was needed. Then I rewrote the agent's rules. The biggest change: a component extends its MUI base instead of copying the Figma picture. The rest stop it guessing: take the MUI API from MUI's documentation server, never from memory; map every Figma value to the exact token; measure the render against Figma before calling it done. The important rules became tests that render each component and fail the build on a hard-coded colour, a raw MUI import where we have a component, or a stateless component holding state.

That fixed the components. Then I realised we didn't need most of them. I wrote a guide for building new components that starts from one idea: the design system is the theme, not the components. Every component falls into one of five types, and you always pick the lightest one that works: the theme first, then a slot, and composition last.

TypeWhat it isExamples
Theme onlyMUI's own component, re-exported. All the design lives in the theme, built from tokens.Switch, Tabs, Dialog, TextField, Select
Styled extensionMUI plus the one thing Figma needs that MUI doesn't have, as a single prop the theme reads.Avatar sizes, Chip variants, IconButton variants
Theme augmentationA paid MUI X component, themed the same way.TreeView, DataGrid
Slot overrideOne piece of MUI's render tree doesn't match Figma, and MUI exposes it as a slot. A small component fills the slot. Nothing wraps the whole thing.The date picker's action bar and day cell
CompositionA new component assembled from design-system parts, for things MUI doesn't offer.Sidebar, Topbar, Stepper, Drawer

The reason is rework. Every custom wrapper is an API teams have to migrate to and we have to keep in step with MUI. With the design in the theme, teams keep importing straight from MUI and still get the look, so adopting it is a theme swap, not a rewrite. Composition is only for what MUI doesn't have; as the guide puts it, composition is the trap. The slot rule came out of review: most of what looked like “MUI can't do this” was a slot nobody had wired yet.

Breadcrumbs went from 289 lines to 20. Three custom group components were deleted outright, because MUI's form controls already did their job.

Adoption and contribution

The architecture was chosen for what adoption costs a team. The design lives in the MUI theme, so a product adopts the system by installing the theme and keeps importing MUI as before. Nothing is rewritten. Four products run on it today.

Since May, nine components have been added by that route (Alert, Drawer, DataGrid, Card, DatePicker, Sidebar, Header, Stepper and Topbar), each with its type on its Storybook page. The one API change consumers saw was the kind you want: <Button label="Save" /> became <Button>Save</Button>, because the component became MUI's own. The rules file that agents build from ends with a table of every mistake an agent has made so far, each paired with the rule that now prevents it: eighteen so far, each a real bug from an earlier session. The guide works the same way. Every rule in it came out of a code review, and there are nineteen: no prop that encodes hover or focus, typed props after the spread so a consumer can't break the contract by accident, hover actions rendered and hidden rather than mounted on hover so they stay in the tab order, nothing hard-coded down to a 4px gap. Products move over page by page, the sidebar first, then the top bar, then the busiest page, so each step is tested on its own.

The rule I'd carry into any rebuild: decide what “done” means first, then test for that before anything is generated.
