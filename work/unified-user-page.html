    The problem

    The suite was four powerful tools that didn't talk to each other: a search tool, a map, a link graph and a log viewer. To answer "what did this account do last Tuesday?", an analyst opened all four, searched the same identifier in each, and stitched the answer together in their head. Some details only lived in the log viewer. Customer feedback said it plainly:

    "Time basis is very important. It's hard to see a timeline with the current tools."Customer feedback, before the project

    Before proposing anything, I checked that story properly.

    Research

    How analysts actually work

    1. Sessions with real analysts. Internal and external fraud analysts walked me through live investigations: each step, where it hurt, and the moment they left our product for another tool.
    2. A journey map across every product. Not just the investigation tool but the case-management and identity products around it, checked with the teams who own them.
    3. Personas and an ideal flow. Lo-fi mockups built around four jobs, deliberately not limited by what the current products could do.
    4. Validation before rendering. Analysts and stakeholders reviewed the lo-fi flow before anything was drawn in high fidelity.

    Psych note

    A little effort on screen, a lot of trust in memory

    When checking the screen costs even a little more effort than recalling, people go from memory, and memory is the less accurate of the two. Every tab switch made checking the costlier option. Put the timeline on one screen and checking becomes a glance.

    Gray, W. D., & Fu, W.-T. (2004). Soft constraints in interactive behavior: The case of ignoring perfect knowledge in-the-world for imperfect knowledge in-the-head. Cognitive Science, 28(3), 359–382.
    The proposal

    A timeline as the spine

    One page with everything about a user (or a device) on it, so an investigation no longer means opening tabs. The organising element is the timeline: every card hangs off it, and the time range you pick drives what every card shows. Change the range once and the map, the KPIs, the transaction list and the analysis cards all follow.

    The proposal became the first pillar of a multi-year "one back office" strategy, with AI tooling and explainability to follow. So the page had to leave room for AI features that didn't exist yet. The first of them, an ask bar that turns a question into filters, arrived a year later and landed on exactly the structure this page set up.

    The lesson

    Find the organising element first.

    Once the timeline was the spine, every other layout question got easier, and the features that came later had somewhere to go.

    From V1 to MVP

    Three rounds with the people who'd use it

    • V1 of the investigation view, reviewed with analysts and product.
    • Feedback round. Analysts found the first version ambiguous: it wasn't clear which cards the timeline applied to. I reworked the layout and hierarchy so the scope of the timeline is visible, not implied.
    • MVP. A final annotated design using the component library, which I then built.
    • After launch. Fixes driven by observed confusion, and analytics events on every new card so the next iteration starts with usage data instead of opinions.
    Extending it

    New signals had a home

    Once the page existed, new findings had an obvious place to appear. When a device-integrity feature started detecting duplicate devices, I designed how that shows up on the page and in the link graph: a toggle for the feature, a switch between clustered and unclustered views, duplicates collapsed into one expandable node, and a copy-all action wherever a list of devices appears. I built the interactions as a Figma Make prototype so engineers and stakeholders could try them instead of reading about them.

    The outcome

    The page shipped as the first pillar of a multi-year back-office strategy, with analytics events on every card so the next iteration starts from usage instead of opinions. A year later the ask bar landed on the structure it set up. I built it in the same codebase the rest of the team ships from, which is the fastest feedback loop I know. The habit I kept: validate on paper. Lo-fi flows reviewed by real analysts saved at least one full redesign.
