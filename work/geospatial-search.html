A map that stopped lying about “no results”

Two chapters on the same map. First, designing a way for analysts to search by geohash, a string that encodes a location at variable precision. Second, auditing the live map with replay data and turning twenty-one observed failures into a prioritised fix list.

Chapter one: searching by geohash

Analysts needed to ask the map "what happened here" where "here" was a geohash: a short string whose length is its precision. Four characters is a region; ten is a doorstep. The design problem was making an abstract code feel like a place you can explore.

MVP requirements I set

  • One geohash at a time. Show its area on the map and the sub-cells inside it, but not the cell characters, which are noise at a glance.
  • Hover a cell for a metadata tooltip.
  • Click a cell to refine. The string in the search bar updates and the results refresh.
  • Edit the string directly, add or remove characters, and the map follows. Minimum four characters, maximum ten.

Out of scope for the MVP, but written down: saving geohashes as polygons, deriving geohashes from a drawn polygon, and showing neighbours. That kept the first release small enough to ship.

Phases two and three

User feedback drove the follow-ups. The most requested was a way back to the original precision after clicking into finer cells, without retyping. Then a heatmap view, with one problem left open: zoomed out, many small geohashes are hard to tell apart.

The map and the search string are the same query: change one and the other updates.

Chapter two: auditing the live map

A year later the map had a new version, more filters and a steady stream of "it says no results but there's data" complaints. I audited it with session replays and customer feedback, logging every failure with its severity, affected version and source.

The pattern behind the complaints

Most of the high-severity issues had one root: rapid pan and zoom cancelled in-flight requests, the app didn't retry, and the UI rendered the cancellation as "No results found". Data existed at that viewport. Pins came back only after zooming out, refreshing, or reapplying filters. In a meaningful share of sessions with active map interaction, the map lied.

Related failures compounded it: a loading banner that never resolved when competing calls left state inconsistent, pins vanishing at deep zoom on small clusters, and a rendering crash that turned the viewport black until refresh.

The quieter, medium-severity ones

  • Advanced filters persisted silently across searches, so users got empty results and had to open a panel to discover why.
  • A "show all activities" button behaved as a toggle; a second click re-applied the filter. Some users clicked it several times.
  • The date picker gave no immediate confirmation, so people opened and closed it repeatedly. A default range of fifteen minutes was too narrow to ever show much.
  • Users accidentally entered polygon-drawing mode and couldn't see how to leave it.
  • A plus sign in an identifier wasn't URL-encoded when navigating from a profile, so the search silently failed.

Turning the audit into design rules

ObservedRule
Cancelled request rendered as "no results"A cancelled or pending request is a loading state, never an empty state. Empty means the server said empty.
"No results" message disappeared too fast to readMake the empty state obvious and persistent; it's a signal, not a toast.
Stale filters and stale search inputAnything that narrows results must be visible where results appear. Add "apply all" and clear-everything affordances.
Default range too smallDefault to twenty-four hours; cap at a year with an explanation.
Toggle button confusion"Show all" is an override that clears filters, not a mode.
Accidental polygon modeDelete key removes a polygon; fewer apply-then-save steps.

Each row became either a ticket linked from the audit, a "UI update in progress" note, or an explicit "not a bug, but reconsider" decision. Engineering fixed the request-cancellation handling first; the design rules shaped the interface work that followed.

Also on this map

Alongside the audit I designed the flow for tagging map boundaries (marking an area as a named zone to reuse later), and added analytics events to the boundary and case-management cards so the next audit starts with real numbers.

What I learned

  • Empty and loading are different states. Conflating them is the single most trust-damaging thing a data UI can do.
  • Write the out-of-scope list down. The geohash MVP shipped because the interesting ideas had somewhere to live that wasn't the first release.
  • Severity plus version plus source is the minimum a UX audit needs to be actionable by engineers, not just persuasive to designers.
